# Windows/Linux Installer Packaging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a Windows NSIS `.exe` installer and a Linux `.deb` package on tagged
releases, built via `cargo-packager`, using a new app icon (a terminal-window +
caracal-ear mark) that the project currently lacks entirely.

**Architecture:** A master SVG icon is rasterized once (locally, via a checked-in
script) into the PNG/`.ico` assets both formats need. A `build.rs` embeds the
`.ico` into the compiled Windows `.exe` itself (separate from what
cargo-packager does — it only sets the *installer's* icon, not the app
binary's). `cargo-packager` config lives in `Cargo.toml`'s
`[package.metadata.packager]` tables and is invoked via `cargo packager
--release --formats <nsis|deb>` from the existing per-OS CI matrix, gated to
tag pushes only.

**Tech Stack:** `cargo-packager` 0.11 (installed via `cargo install
cargo-packager --locked`), `winresource` 0.1 (Windows-only build-dependency),
`rsvg-convert` + ImageMagick `magick` (local, one-time icon rasterization —
not a build-time or CI dependency).

## Global Constraints

- Maintainer / authors: `EricX-Zhao <uupks0325@gmail.com>` (exact string, used
  verbatim in the `.deb` control file's `Maintainer` field).
- Windows: NSIS `.exe` only (no WiX `.msi`), install mode `currentUser`,
  installer languages `English` + `SimpChinese`.
- Linux: `.deb` only (no AppImage/Pacman in this pass).
- Packaging only runs in CI on tag pushes (`refs/tags/v*`) — never on plain
  `main` pushes or PRs.
- The existing raw-binary artifacts (`caracal-windows-x86_64.exe`,
  `caracal-linux-x86_64`) are kept; installers are additive.
- Icon mark: dark rounded-square badge `#1c1c1e` background, off-white
  `#f2ede6` foreground (terminal window outline + two tufted ears + `>_`
  prompt). This exact geometry/color was approved during brainstorming — do
  not redesign it.
- All commands and TOML/Rust snippets below were run against this actual repo
  during planning (`cargo-packager` 0.11.8, this repo's real `Cargo.toml`) and
  their outputs verified — they are not guesses.

## File Structure

| File | Responsibility |
|---|---|
| `assets/icon/caracal-mark.svg` | Master vector icon — single source of truth for every generated size. |
| `scripts/generate-icons.sh` | Rasterizes the master SVG into every PNG size + the multi-res `.ico`. Run locally, not in CI. |
| `assets/icon/icon-{16,24,32,48,128,256,512}.png`, `assets/icon/caracal.ico` | Generated, checked-in outputs consumed by `cargo-packager`. |

| `Cargo.toml` | Gains a Windows-only `build-dependencies` table (Task 2) and `[package.metadata.packager]` + `.deb`/`.nsis` subtables (Task 3). |
| `.github/workflows/build.yml` | Gains tag-gated packaging steps in the existing `build` job matrix. |
| `README.md` | "Prebuilt binaries" section mentions the new installers. |

- [ ] **Step 2: Write the generation script**

Create `scripts/generate-icons.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Regenerates assets/icon/*.png and assets/icon/caracal.ico from the master
# SVG (assets/icon/caracal-mark.svg). Requires `rsvg-convert` (librsvg) and
# ImageMagick's `magick` on PATH. Run from anywhere; outputs are checked
# into git and are NOT regenerated in CI — only re-run this after editing
# the master SVG.

cd "$(dirname "$0")/.."

SRC="assets/icon/caracal-mark.svg"
OUT="assets/icon"

for size in 16 24 32 48 128 256 512; do
  rsvg-convert -w "$size" -h "$size" "$SRC" -o "$OUT/icon-$size.png"
done

# Windows .ico max standard frame size is 256x256 — 512 isn't included here.
magick "$OUT/icon-16.png" "$OUT/icon-24.png" "$OUT/icon-32.png" \
       "$OUT/icon-48.png" "$OUT/icon-256.png" "$OUT/caracal.ico"

echo "Generated:"
ls -la "$OUT"/icon-*.png "$OUT/caracal.ico"
```

- [ ] **Step 3: Make it executable and run it**

Run:
```bash
chmod +x scripts/generate-icons.sh
./scripts/generate-icons.sh
```
Expected: prints an `ls -la` listing of 7 PNGs + `caracal.ico`, no errors. If
`rsvg-convert`/`magick` aren't installed, install `librsvg` and `imagemagick`
via the system package manager first (both are available as standard distro
packages; on this project's Ubuntu CI image they'd be `librsvg2-bin` and
`imagemagick`, but this script only ever runs locally, never in CI).

- [ ] **Step 4: Verify the outputs**

Run:
```bash

```
Expected: each PNG reports its own size as `RGBA` (e.g. `icon-256.png: PNG
image data, 256 x 256, 8-bit/color RGBA, non-interlaced`), and
`caracal.ico: MS Windows icon resource - 5 icons, 16x16, 32 bits/pixel, ...`.

- [ ] **Step 5: Commit**

```bash

git commit -m "feat: add app icon (terminal-window + caracal-ear mark)"
```

### Task 2: Embed the icon into the Windows `.exe`

Why this is a separate step from Task 3: `cargo-packager`'s `nsis.installerIcon`
(Task 3) only sets the icon the *installer wizard* displays — it does not
patch the compiled binary itself. Without this task, the installed
`caracal.exe` would show a blank/default icon in Explorer, the taskbar, and
Start Menu shortcuts (which inherit their icon from the target `.exe`).

**Files:**
- Create: `build.rs`
- Modify: `Cargo.toml` (add a Windows-only `build-dependencies` table)

**Interfaces:**
- Consumes: `assets/icon/caracal.ico` (from Task 1).

- [ ] **Step 1: Add the Windows-only build-dependency**

In `Cargo.toml`, after the existing `[dependencies]` block's last line
(`env_logger = "0.11"`), add a new top-level table:

```toml

[target.'cfg(windows)'.build-dependencies]
winresource = "0.1"
```

- [ ] **Step 2: Write build.rs**

Create `build.rs` (repo root, next to `Cargo.toml`):

```rust
fn main() {
    #[cfg(windows)]
    {
        let mut res = winresource::WindowsResource::new();
        res.set_icon("assets/icon/caracal.ico");
        res.compile().expect("failed to embed Windows icon resource");
    }
}
```

- [ ] **Step 3: Verify the Linux build still succeeds (no-op branch)**

Run:
```bash
cargo check --release --locked
```
Expected: succeeds exactly as before (`winresource` is a Windows-only
build-dependency, so it isn't even downloaded/compiled on Linux; `build.rs`'s
`main()` body is empty on this platform). This does **not** verify the icon
actually gets embedded — that only happens when compiling for Windows, which
this dev machine can't do. Real verification is: after the first Windows CI
build post-merge, right-click the produced `caracal.exe` in Windows Explorer
→ Properties, and confirm the icon tab shows the caracal mark instead of the
default Rust/generic binary icon.

- [ ] **Step 4: Commit**

```bash
git add build.rs Cargo.toml Cargo.lock
git commit -m "feat: embed app icon into the Windows exe via winresource"
```

### Task 3: `cargo-packager` configuration (Cargo.toml + deb desktop template)

**Files:**
- Modify: `Cargo.toml` (add `[package.metadata.packager]` and its `.deb`/
  `.nsis` subtables)
- Create: `packaging/linux/desktop-entry.hbs`

**Interfaces:**
- Consumes: `assets/icon/icon-*.png`, `assets/icon/caracal.ico` (Task 1).
- Produces: a working `cargo packager --release --formats deb` /
  `--formats nsis` invocation that Task 4's CI step calls verbatim.

Context worth knowing before writing this (confirmed by reading
`cargo-packager` 0.11.8's actual source, not just its docs, and by running it
against this repo):

- `productName`, `identifier`, `authors`, `longDescription`, `outDir`, and
  `icons` are **not** auto-derived from `[package]` in a way we want, so they
  need explicit values. But `version`, `description`, and `binaries` **are**
  auto-filled from `[package]` (version/description) or auto-detected (the
  single `caracal` binary target) — do not set those explicitly, it would
  just be duplication that can drift.
- `binariesDir` also auto-resolves to `target/release` when `--release` is
  passed — don't set it either.
- `nsis.installMode`'s canonical TOML key is `installMode` (camelCase). The
  configuration docs site shows `install-mode` (kebab-case) — that is **not**
  a valid alias for this particular field (the actual kebab-case alias in the
  source is `installer-mode`, an inconsistency in the crate itself). Use
  `installMode` to sidestep the ambiguity entirely.
- The `depends` list below was derived by running `ldd`/`objdump -p` against
  this repo's actual release binary, mapping each `NEEDED` entry to its
  owning Ubuntu 22.04 package, plus `libvulkan1` and `libfontconfig1` (both
  dlopen'd at runtime by `wgpu`/`font-kit` respectively, so they don't show
  up in `ldd` — their inclusion is evidenced by `build.yml`'s existing Linux
  dependency list already installing `libvulkan1` as a bare runtime package,
  not a `-dev` header package, alongside `font-kit`'s well-known fontconfig
  dependency on Linux). Each of the 11 package names was independently
  confirmed to actually provide the expected `.so` inside a real
  `ubuntu:22.04` container via `dpkg -L <package> | grep .so`.

- [ ] **Step 2: Add the custom Debian desktop-entry template**

`cargo-packager`'s built-in `AppCategory` enum has no "terminal emulator"
category — the closest built-in options collapse to a coarse `Development;`
or `Network;` string, losing the `TerminalEmulator` freedesktop category that
lets desktop environments treat Caracal as a terminal app (e.g. "open
terminal here" integrations). A custom template hardcodes the exact
categories we want instead.

Create `packaging/linux/desktop-entry.hbs`:

```handlebars
[Desktop Entry]
Categories=Utility;TerminalEmulator;Network;
Exec={{exec}} {{exec_arg}}
Icon={{icon}}
Name={{name}}
Terminal=false
Type=Application
```

- [ ] **Step 1: Add packaging steps to the `build` job**

In `.github/workflows/build.yml`, insert three new steps between the existing
"Prepare artifact" step and "Upload artifact" step (i.e. after line 96,
before line 98 in the current file):

```yaml
      - name: Install cargo-packager
        if: startsWith(github.ref, 'refs/tags/v')
        run: cargo install cargo-packager --locked

      - name: Package Windows installer
        if: startsWith(github.ref, 'refs/tags/v') && runner.os == 'Windows'
        run: cargo packager --release --formats nsis

      - name: Package Linux .deb
        if: startsWith(github.ref, 'refs/tags/v') && runner.os == 'Linux'
        run: cargo packager --release --formats deb
```

- [ ] **Step 2: Broaden the artifact-upload path**

The existing "Upload artifact" step only uploads the single renamed raw
binary:

```yaml
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: ${{ matrix.asset_name }}
          path: dist/${{ matrix.asset_name }}
          if-no-files-found: error
```

Change `path` to pick up everything now landing in `dist/` (the raw binary on
every run, plus the installer on tag runs — each OS's `dist/` only ever
contains that OS's own files, so this can't cross-contaminate between the
Windows and Linux matrix jobs):

```yaml
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: ${{ matrix.asset_name }}
          path: dist/*
          if-no-files-found: error
```
