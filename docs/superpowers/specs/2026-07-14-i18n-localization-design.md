# i18n localization (Chinese + English)

## Background

Every user-facing string in the app — menu labels, tooltips, panel titles,
placeholders, error/status messages, window titles — is a hardcoded
Simplified Chinese string literal, scattered across ~16 files (~220 call
sites). There is no translation layer today. `rust-i18n` already sits in the
dependency tree transitively (pulled in by `gpui-component`, which uses it
internally for its own small set of built-in strings via
`crates/ui/locales/ui.yml`), but caracal doesn't call its own `i18n!()` or
use `t!()` anywhere.

Two things were verified directly (not assumed) before writing this spec:

1. **Multiple `i18n!()` calls in the same binary don't conflict.** The
   `t!()` macro (exported by the `rust_i18n` crate) expands to
   `crate::_rust_i18n_t!(...)` — a crate-local item generated by whichever
   crate's own `i18n!()` call is in scope. gpui-component's internal
   `t!("Dock.Unnamed")`-style calls resolve against *its own* crate-local
   backend and locale files; our own `i18n!()` call and `locales/app.yml`
   are completely independent. (Confirmed further by the fact `Cargo.lock`
   already carries two different `rust-i18n` versions — 3.1.5 and 4.1.0 —
   for different dependents, which wouldn't be possible if the macro
   generated anything shared across crates.)
2. **The current locale defaults to the OS locale, not `i18n!()`'s
   `fallback` parameter.** Ran a throwaway trial: with `LANG=en_US.UTF-8`
   set (this dev machine's actual env) and `i18n!("locales", fallback =
   "zh-CN")`, `t!("Test.hello")` returned the *English* string before any
   `set_locale()` call — `fallback` only kicks in when a specific locale is
   missing a given key, it is **not** the initial active locale. This means
   the app must explicitly call `rust_i18n::set_locale(&persisted_language)`
   at startup, exactly like the existing `apply_startup_theme` pattern —
   it cannot rely on `i18n!()`'s defaults to land on the user's saved
   preference.

Also verified: `t!(...)` returns something that converts to
`gpui::SharedString` via a plain `.into()` (confirmed by a real
`cargo build` — `let s: SharedString = rust_i18n::t!("Test.hello").into();`
compiles and runs correctly, printing the right string in each locale).

## Decisions (confirmed with user)

- **Full conversion in one pass** — every one of the ~220 existing
  hardcoded-Chinese call sites gets converted, not a partial/core-chrome-only
  first cut.
- **Chinese and English only** for now (matches the request; the locale
  file format supports adding more languages later without restructuring).
- Chinese-language **code comments** (including ones written earlier this
  session) are explicitly **out of scope** — they aren't user-facing.

## Architecture

### Dependency + setup

- `Cargo.toml` gains a **direct** `rust-i18n = "4"` dependency (previously
  only transitive via `gpui-component`).
- `main.rs` (crate root) gets one macro call, near the top of the file:
  `rust_i18n::i18n!("locales", fallback = "zh-CN");` — `"locales"` is a
  path relative to `CARGO_MANIFEST_DIR`, i.e. `<repo-root>/locales/`.

### Locale file: `locales/app.yml`

Single file, `_version: 2` nested format — the same style
`gpui-component`'s own `crates/ui/locales/ui.yml` already uses (inline
`zh-CN:`/`en:` values side by side per key, easy to keep both languages in
sync when editing). Top-level keys mirror the module that owns the string,
so a translator (or future-you) can find a string by module without
grepping:

```yaml
_version: 2
Header:
  settings_tooltip:
    zh-CN: "设置"
    en: "Settings"
ActivityBar:
  file_explorer:
    zh-CN: "文件浏览器"
    en: "File Explorer"
Sessions:
  title:
    zh-CN: "会话"
    en: "Sessions"
  empty_state:
    zh-CN: "暂无会话,点 + 新增"
    en: "No sessions yet — click + to add one"
Sftp:
  status_row:
    zh-CN: "共 %{count} 项 | %{size}"
    en: "%{count} item(s) | %{size}"
Settings:
  General:
    language_label:
      zh-CN: "语言"
      en: "Language"
```

Namespaces used, one per source module: `Header`, `ActivityBar`, `Sessions`,
`Sftp`, `Settings` (with `General`/`Appearance`/`Terminal` sub-sections
matching the existing tab split), `Terminal` (the terminal-view chrome, not
tab content), `Workspace`, `Monitor`, `QuickCommands`, `NewConnectionWindow`,
`Icons` (tooltip-only text not already covered by a panel's own namespace).

### Call-site conversion pattern

Every replaced string follows one of two shapes:

**Static text** (no interpolation) — direct `.into()`:

```rust
// Before
.child("会话")
// After
.child(SharedString::from(t!("Sessions.title")))
```

(`t!(...)` already converts via a plain `.into()`; wrapping in
`SharedString::from(...)` at call sites that need an explicit type — e.g.
a `let` binding used more than once — keeps things unambiguous. Where a
builder method accepts `impl Into<SharedString>` directly, passing
`t!(...)` bare also works and is preferred for brevity.)

**Interpolated text** — `t!()`'s own named-variable substitution replaces
`format!()`:

```rust
// Before
let summary = format!("共 {count} 项 | {}", human_size(total_bytes));
// After
let summary = t!("Sftp.status_row", count = count, size = human_size(total_bytes));
```

### Settings integration (`settings.rs`, `settings_window.rs`)

- New `GeneralSettings { language: String }` in `settings.rs`
  (`#[serde(default = "default_language")]`, default `"zh-CN"`) — `AppSettings`
  gains a `general: GeneralSettings` field alongside the existing
  `appearance`/`terminal`. Old `settings.toml` files without a `[general]`
  table just get the default, same backward-compat convention already used
  for every other settings field in this file.
- `settings_window.rs`'s General tab (currently
  `render_placeholder_tab("General", cx)`) becomes a real
  `render_general_tab`, with one language dropdown — same `DropdownButton` +
  `.dropdown_menu(...)` idiom as the theme dropdown, offering exactly two
  entries: 简体中文 (`"zh-CN"`) / English (`"en"`).
- `apply()` (already the place `Theme::change`/`apply_config` +
  `cx.refresh_windows()` happen for the appearance tab) gains one more line:
  `rust_i18n::set_locale(&self.draft.general.language);` before the existing
  `cx.refresh_windows()` call — reuses the *exact* refresh mechanism already
  proven for the theme-staleness bug fixed earlier this session (every
  `t!()` call sits inside a `render()`, so forcing every window to repaint
  is sufficient; no per-string reactivity needed).
- `main.rs`'s startup sequence calls
  `rust_i18n::set_locale(&startup_settings.general.language)` right after
  `apply_startup_theme(...)`, for the reason established above (the OS
  locale, not the persisted preference, is what's active otherwise).

### Per-file conversion

Every file in this list gets every hardcoded Chinese string literal
extracted to `locales/app.yml` and replaced with a `t!(...)` call, verified
by a final `grep -P '[\x{4e00}-\x{9fff}]'` pass per file showing zero
matches inside string literals (Chinese comments are expected to remain and
are not a failure):

`panels/header.rs`, `panels/activity_bar.rs`, `panels/sessions.rs`,
`panels/sftp.rs`, `panels/settings_window.rs`, `panels/terminal.rs`,
`panels/monitor.rs`, `panels/quick_commands_panel.rs`,
`panels/new_connection_window.rs`, `panels/stub.rs`, `panels/icons.rs`
(tooltip strings only — `AppIcon` itself stays as-is), `workspace.rs`,
`settings.rs` (validation error messages), `terminal/view.rs` (connection
banner text), `config.rs`, `assets.rs`.

## Testing

- No automated test can verify "the UI shows the right text in the right
  language" — matches this codebase's existing convention of manual
  verification for `render()`-level UI.
- Any small pure logic extracted along the way (e.g. a
  `language_display_name(code: &str) -> &'static str` used by the General
  tab's dropdown button label) gets ordinary unit tests, same convention as
  `header.rs`'s `maximize_icon`/`or_default_layout`.
- `settings.rs` gets the usual round-trip/backward-compat tests for the new
  `general.language` field, matching the existing pattern for every other
  field in that file (missing-file default, partial-TOML default, explicit
  round-trip).
- Manual verification: open Settings → General, switch to English, Apply,
  confirm the whole app (header, both activity bars, sessions panel, SFTP
  panel, terminal chrome, quick commands, settings window itself) re-renders
  in English immediately without a restart; switch back to Chinese; restart
  the app and confirm the persisted language survives.

## Non-goals

- No language beyond Chinese/English.
- No translation of Chinese-language code comments.
- No changes to `gpui-component`'s own internal strings/locale file (out of
  our control, separate crate) — though switching `rust_i18n`'s global
  current-locale *does* also affect gpui-component's own `t!()` calls
  incidentally, since `set_locale` is a single process-wide global; this is
  a harmless bonus, not something we build for.
- No RTL layout support (not needed for zh-CN/en).
