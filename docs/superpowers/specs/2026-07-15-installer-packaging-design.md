# Windows/Linux installer packaging via cargo-packager

## Background

Caracal's [build.yml](../../../.github/workflows/build.yml) currently
produces bare binaries only: `cargo build --release` on `windows-latest`
and `ubuntu-22.04`, renamed to `caracal-windows-x86_64.exe` /
`caracal-linux-x86_64`, and attached to tagged GitHub Releases as-is. There
is no installer — a Windows user gets a naked `.exe` to run from wherever
they downloaded it, and a Linux user gets a naked ELF binary with no
`.desktop` entry or menu integration.

The project also has no application icon today. `assets/icons/*.svg` are
small in-app UI glyphs (pencil, folder, trash, etc.), not a logo — there is
nothing to put on an installer, a taskbar entry, or a `.desktop` file.

## Decisions (confirmed with user)

- **Tool**: [cargo-packager](https://github.com/crabnebula-dev/cargo-packager)
  (`cargo packager --release`), configured via
  `[package.metadata.packager]` in `Cargo.toml`. Chosen over `cargo-dist`
  (CLI-tool-oriented, weaker on desktop-app installer conventions like
  Start Menu shortcuts / `.desktop` entries) and over hand-rolling
  `cargo-wix` + `cargo-deb` separately (two tools/configs to maintain vs
  one).
- **Windows format**: NSIS `.exe` only. No WiX `.msi` — one Windows
  installer format is enough, and NSIS is the one that matches "exe
  installer" from the original ask.
  - Install mode: **per-user** (`installMode: currentUser`) — no UAC
    elevation, matches how a single-developer desktop tool is normally
    installed.
  - Installer UI languages: `en` + `zh-CN`, matching the app's own
    [locales/app.yml](../../../locales/app.yml) language pairs.
- **Linux format**: `.deb` only. AppImage/Pacman are not part of this pass
  (nothing currently asks for them; can be added later by adding formats to
  the same config, not a redesign).
  - `.desktop` entry: auto-generated by cargo-packager (`generateDesktopEntry`
    default), category `Utility;TerminalEmulator;Network;`.
  - `depends`: cargo-packager does **not** auto-detect shared-library
    dependencies the way `cargo-deb`'s `$auto` does — its `depends` field is
    a manual list (confirmed against
    [DebianConfig docs](https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.DebianConfig.html)).
    The implementation step must run `ldd` against the actual
    `ubuntu-22.04`-built release binary and hand-write the resulting
    package names into `depends`, rather than guessing from the *build-time*
    `apt-get install` list already in `build.yml` (those are `-dev` headers
    needed to compile, not the runtime `.so` package names).
- **Maintainer**: `EricX-Zhao <uupks0325@gmail.com>` (from git config).
- **CI trigger**: only on tag pushes (the existing `release` job gated on
  `refs/tags/v*`), not on every `main` push/PR. The `build` job keeps doing
  plain `cargo build --release` + `cargo test` on every push — packaging
  adds real time (icon conversion, NSIS/dpkg invocation) that isn't worth
  paying on every commit.
- **Artifact policy**: additive, not a replacement. The existing bare
  `caracal-windows-x86_64.exe` / `caracal-linux-x86_64` binaries stay in
  the Release (for people who want a portable binary / to place it on
  `PATH` themselves); the new `.exe` installer and `.deb` package are
  uploaded alongside them.

## App icon design

A hybrid mark: a terminal window with caracal-style tufted cat ears.

- **Shape**: a rounded-rect terminal window outline with two small
  triangular ears (plus a short tuft line at each ear tip, echoing the
  caracal's signature ear tufts) growing from its top-left/top-right
  corners, and a `>_` prompt glyph inside the window.
- **Color**: fixed (non-theme-adaptive) dark rounded-square badge
  (`#1c1c1e`) with an off-white mark (`#f2ede6`) drawn on top — chosen over
  a badge-less transparent icon because a mono-color mark with no
  background disappears against similarly-toned desktop backgrounds/taskbars
  (verified via mockup: the badge-less variant nearly vanished on both a
  light and a dark simulated taskbar row).
- **Small-size handling**: the `>_` prompt is kept at every size, including
  the smallest (16px system-tray). Since `.ico` bakes a distinct bitmap per
  resolution anyway, the 16px layer gets its own hand-tuned render (thicker
  strokes / larger glyph proportions) at icon-generation time rather than a
  naive downscale of the 256px master — this is an implementation detail,
  not a design fork.
- **Source of truth**: a single master SVG (new file, e.g.
  `assets/icon/caracal-mark.svg`) at a large canvas (e.g. 512×512),
  rasterized to the platform-specific formats below. The 4 rejected
  direction sketches and color/badge comparisons from the brainstorming
  session live in `.superpowers/brainstorm/` (gitignored, not part of the
  shipped design).

### Generated assets

| Platform | Format | Sizes | Used by |
|---|---|---|---|
| Windows | `.ico` | 16, 24, 32, 48, 256 | NSIS installer + exe file icon |
| Linux | `.png` | 32, 128, 256, 512 | `.deb` `.desktop` entry / icon theme |

Both are generated from the master SVG (e.g. via `resvg` + `ico-builder`,
or an equivalent conversion step) and checked into the repo under
`assets/icon/` rather than generated on every CI run, so the icon is
inspectable and stable across builds.

## CI changes

`build.yml`'s `release` job (currently: download artifacts → create GitHub
Release) grows a per-OS packaging step **before** artifact upload, added to
the existing `build` job's matrix (since packaging needs the same
already-built release binary and the same native host — WiX/NSIS only run
on Windows, `dpkg-deb` only runs on Linux, so no cross-compilation is
introduced):

1. After `cargo build --release --locked` (existing step), run
   `cargo packager --release` on tag builds only (`if: startsWith(github.ref, 'refs/tags/v')`).
2. Add the produced `.exe` (NSIS) / `.deb` to the same `dist/` directory
   already used for the renamed raw binary, so the existing
   "Upload artifact" → "Create GitHub Release" steps pick them up with no
   further changes.
3. `cargo-packager` itself needs installing (`cargo install cargo-packager
   --locked`, cacheable the same way the Rust toolchain already is).

No new runners, no new jobs, no cross-compilation — each OS's existing
runner produces its own installer for its own OS, same as it already does
for the raw binary.

## Testing / verification

- **Windows**: run the generated NSIS `.exe` in a VM/test machine, confirm
  it installs per-user without UAC, creates a Start Menu entry with the new
  icon, and that the icon renders correctly at taskbar and Start Menu
  sizes.
- **Linux**: `dpkg -i` the generated `.deb` on an Ubuntu 22.04 (and ideally
  24.04) machine/container, confirm it installs without missing
  dependencies (the `ldd`-derived `depends` list is the thing most likely
  to be wrong — an unresolved `.so` at launch is the failure mode to watch
  for), and that the app appears in the desktop menu with the icon.
- Both installers get exercised manually before the first tagged release
  that ships them — this is infrastructure a CI unit test can't meaningfully
  cover.

## Out of scope

- macOS packaging (`.dmg`) — `build.yml` has no macOS runner today; adding
  one is a separate decision.
- Auto-update (`cargo-packager-updater`) — not requested, and it implies a
  hosted update manifest this project doesn't have yet.
- WiX `.msi` for Windows — NSIS covers the "exe installer" ask; adding a
  second Windows format is low value without a specific reason.
- AppImage / Pacman for Linux — not requested; can be added later as more
  `formats` entries in the same `packager` config.
